Unit 12 / Software Development

Currency Exchange Calculator: reading and debugging two VB.NET programs

Taking two supplied Windows Forms programs apart to see how they work, rebuilding them in Visual Studio, finding three defects, and writing up what I would change about how they were put together.

Analysed and designed

What this page is, and is not

The wider brief for this unit is a currency exchange calculator for Sussex Software Solutions Limited, building for a local travel agent. The program has to convert between pounds and a foreign currency in both directions, let the user edit the exchange rates, and show the converted amount alongside the rate that produced it.

I have not built that program. What I completed is the first assignment, which is an analysis of two supplied VB.NET programs: how they work, what language constructs they use, and how good the code is. That is real work and I am pleased with it, but a page claiming a finished currency converter would be describing something that does not exist.

I did write, build, debug and run VB.NET for this: I rebuilt both supplied programs in Visual Studio, corrected them and ran them, which is how the screenshots on this page exist.

The two programs

Program 1: frmDiscount

A discount calculator. The user types an amount and a rate, clicks Calculate, and the result appears. It declares amount, discount_rate and result as Decimal, reads both text boxes through CDec, multiplies, and writes the answer back to a third text box. The whole program is one event handler, btnCalculate_Click, bound with Handles btnCalculate.Click.

Program 2: frmSelection

A sales bonus calculator. It reads a sales total and walks an If … ElseIf … Else ladder to decide which bonus message to show: above 150,000 pays 12,000; 90,000 to 149,999 pays 8,000; 50,000 to 89,999 pays 5,000; anything below pays nothing.

The three defects I found

I annotated each one in the code itself, keeping the original line beside the correction so the change is readable rather than just applied.

1. A variable the calculation never sees

The declaration line creates amount, discount_rate and result. But the assignment underneath it reads the rate into rate, which is never declared anywhere.

  • Before: rate = CDec(txtRate.Text)
  • After: discount_rate = CDec(txtRate.Text)

This is the one I like, because nothing about it looks broken. discount_rate simply stays at its default of zero, so result = amount * discount_rate is always zero. The program runs, the button works, and every answer is silently wrong.

2. An event handler bound to nothing

  • Before: Handles btnSubmitClick
  • After: Handles btnSubmit.Click

A Handles clause needs the control and the event separated by a dot. Without it the compiler cannot resolve the binding, so the Submit button is wired to nothing and clicking it does not run the code.

3. Three faults in one line

  • Before: Else If Sales_ Total >= 50000 And Sales_ Total <= 89000 Then
  • After: ElseIf Sales_Total >= 50000 And Sales_Total <= 89999 Then

The keyword was written Else If with a space, which VB.NET reads as a nested If and leaves the block structure unbalanced. The identifier had a stray space in it, Sales_ Total, which will not compile. And the upper bound said 89,000 while the comment directly above it said the band ran to 89,999, so a sales total of 89,500 fell through to the bottom branch and paid nothing.

My written note on this fix only mentions the first two. The boundary value is in the corrected code but I never said why I changed it, which I should have.

One correction to my own write-up: I listed CDec under basic string handling. It is not. CDec converts a value to a decimal; string handling is concatenation, length and substrings. Neither program does any of that.

How good is the code?

Efficiency and performance

  • Both programs are efficient due to simple logic.
  • Calculations and comparisons execute instantly.
  • No unnecessary processing or memory usage.
  • Performance is suitable for small-scale applications.

Maintainability

  • Poor variable naming causes confusion, for example discount_rate against rate.
  • Logic is tightly coupled to the user interface.
  • No reusable functions or modular structure.
  • Errors are harder to detect due to lack of validation.
  • Code would be difficult to scale or extend.

Usability

  • Simple and easy-to-use interface.
  • No guidance or feedback for incorrect input.
  • Application may crash if invalid data is entered.
  • Output is not formatted clearly for users.

What I would change

  • Separate calculation logic from interface code.
  • Fix the variable naming inconsistency.
  • Add input validation using Decimal.TryParse.
  • Prevent program crashes from invalid input.
  • Format output to two decimal places.
  • Add meaningful error messages.

Decimal.TryParse is the one I would do first. CDec throws when it is handed something that is not a number, so typing a letter into the amount box crashes the program. TryParse returns false instead of throwing, which turns a crash into a message.

What is not evidenced here

The second assignment covers the design work for the currency calculator itself: a problem definition, screen designs, navigation, data structures, validation and error handling, a mapping of which controls respond to which events, a data dictionary, pseudocode, a test plan with test data, alternatives and a justification.
