Unit 3 / A Digital Portfolio

This website

The brief is to design and build a digital portfolio for an IT apprenticeship application, test it across browsers and systems, gather feedback, and evaluate the finished thing against the original design. You are reading the build.

In progress

The brief

The scenario is applying for an IT apprenticeship at a local company called Konnekted, which the brief says recruits apprentices. The portfolio has to be hosted so an employer can open it in a browser, be made of linked web pages with one main page the others link to, and be split into sections by the kind of content in them.

One requirement is stated twice, once in the scenario and again at the end of Task 1: The portfolio must include work from all your completed units in the course. That is why there are seven unit pages here and not just the three with finished work on them.

Worth being clear about

Konnekted is named in the brief as the scenario employer. I have not confirmed whether it is a real local company I am applying to or a name written into the assignment, and the framing of this whole site depends on which. I need to check before I describe it as a genuine target employer anywhere.

I built before I documented, which is the wrong order and the opposite of what I did for Unit 13. The design decisions below are real and I can justify all of them, but they exist as a built site rather than as the design document the brief asks for, and that is work still to do.

How this site is built, and why

Everything here is checkable by viewing source, which is the useful thing about a portfolio being the coursework.

Plain HTML, CSS and JavaScript

No framework, no bundler, no build step, no dependencies to install. The site opens correctly by double-clicking index.html from a folder, which matters because it is an assessment deliverable that has to work wherever it is put. It also means nothing between what I wrote and what the browser runs.

One stylesheet, no page styles

The version of this site I started from carried the same 194 lines of CSS copy-pasted into seven separate pages, and more styling in style="" attributes on individual elements. That is 35 kilobytes of CSS that could not be cached and had to be changed in seven places at once. Everything now lives in assets/css/style.css. No page has a <style> block and no element has a style attribute.

Design tokens, and a palette I can defend

Colours, type sizes and spacing are declared once as custom properties on :root. The brand colours are the three I specified and justified for my Unit 13 client site: #007BFF, #FFFFFF and #CCD1D6.

With one change. #007BFF on white measures 3.98:1, and WCAG AA asks for 4.5:1 on body-size text, so links and small text use a darkened #0B57D0 that measures 6.4:1 while #007BFF keeps the large display type and the accents. #CCD1D6 is never used for text; it is the colour of every rule and border on the site, which is where a light grey actually works.

Light and dark

The same tokens are redeclared under prefers-color-scheme: dark, so the site follows whatever the reader's device is set to rather than forcing one.

The status system

Every unit carries one of four labels: built and tested, analysed and designed, in progress, or briefed and studied. It is the organising idea of the whole site. Three units have finished work and four do not, and saying which is which is more persuasive than writing all seven up as though they were the same.

Accessibility

The brief for both this unit and Unit 13 treats accessibility as assessed, so it is built in rather than checked at the end:

  • A skip link, and one <main> landmark per page.
  • The menu button is a real <button> with aria-expanded, so it works from the keyboard. The version I started from used a <div>, which meant nobody navigating by keyboard could open the navigation on a phone at all.
  • When the mobile menu is closed the links are display: none rather than positioned off-screen, so they leave the tab order instead of sending focus somewhere invisible.
  • aria-current="page" marks the current page in the navigation, not just a colour.
  • The image lightbox traps Tab, closes on Escape, and returns focus to whatever opened it.
  • Visible :focus-visible styles on everything focusable.
  • Every text and background pair checked against WCAG AA.
  • prefers-reduced-motion switches off the transitions and smooth scrolling.
  • Real <label> elements on every form field, with errors announced through aria-describedby and a live region.

Performance

Every image has explicit width and height so nothing jumps while the page loads, and everything below the fold is lazy-loaded. The website walkthrough video was 15 MB for 25 seconds; it is now 876 KB, with a poster image and preload="none" so it costs nothing until someone presses play.

Type

Archivo for headings, Source Sans 3 for reading, and JetBrains Mono only where the content is literally code: filenames, identifiers, timecodes and hex values. Each has a real fallback stack so the site still sets properly with no network.

Tasks 2 and 3: testing and reviewing

Task 2 asks for a test plan covering different browsers and different computer systems, worked through with faults recorded and corrected, plus user feedback gathered and acted on. Task 3 asks for a written evaluation comparing the finished portfolio to the original designs, justifying changes and recommending improvements.

Neither is done. The brief also requires a screenshot of the folder structure and for the uploaded portfolio to be witnessed by my tutor.
